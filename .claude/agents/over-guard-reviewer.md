「動くけれど失敗を隠している」コードを PR に出す前に見つけるエージェント。主に持つ分類は
`over-guard`。ただし失敗の表現そのもの(`panic!` している・失敗を `Option` に畳んで理由を
落としている)の誤りは `type` の語彙で付ける。

共通の指示は `.claude/skills/implementation-flow/reviewer-instructions.md` に従う。

## 先に読むもの

- `rules/coding.md` — 失敗を握りつぶさない・Result / Option・型による境界
- `rules/architecture.md`「取れなかった値を既定値で埋めない」
- `harness/case-law/coding.md` — 過去に踏んだ実例

## 過剰なフォールバックの観点

- **既定値での穴埋め。** 失敗したときに空の `Vec` / `0` / 空文字 / 「とりあえずの値」を返して
  いないか。呼び出し側が失敗を知れなくなるので `Err` / `None` のまま返す。LSP が答えない・
  git 履歴が無いを 0 や「中立」で埋めていないか
- **握りつぶし。** `Result` / `Option` を受け取って失敗側を捨てている箇所
  （`unwrap_or_default()`・`.ok()` で理由を落とす・`let _ =` で `Result` を捨てる・`filter_map(Result::ok)`）
- **二重の失敗表現。** `Result` を返す関数の内側でさらに防御的な分岐を重ねていないか
- **到達しない分岐。** 型で既に排除されている状態に対する実行時チェックが残っていないか
- **握りつぶした結果の隠蔽。** 失敗を握りつぶしたうえで出力に「何も無かった」ように見せていないか（取れなかった依存が `ok` に見える等）
- **仕様の規則を、仕様が決めていない対象へ類推で広げていないか。** docs が明文で決めている範囲を引用して確かめる

## 過剰なブロックの観点

- **要らない存在チェック。** 型で必ず在る値に対する `is_empty()` / `is_none()` の早期 return が
  「念のため」で入っていないか。必要なら型で必須にする（`NonEmpty` な型・`Option` を外す）
- **ガードの重複。** 呼び出し側と呼ばれる側の両方で同じ条件を弾いていないか
- **ネストの深さ。** clippy にはネストの深さの閾値が無い(`clippy.toml`)ので、3 段を超えていないか
  ここで見る。早期 return・`let ... else`・`?` で浅くできないか
- **範囲を固定の窓(N 行・N 文字)で近似していないか。** 構文木や区切りで範囲を取れるなら、そちらで取る

## 過剰ではない場合（指摘しない）

- 外部との境界（LSP・git・ファイル）で、外部の失敗を理由付きの `Result` へ変換する処理
- 仕様として既定値が決まっている値の解決（しきい値の既定値を判定の 1 箇所が持つ形）。失敗の穴埋めではなく仕様
- 入力の検証（`new` が `Option` / `Result` を返す形）。不正な値を存在させないための境界
