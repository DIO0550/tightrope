差分が**外部プロセスへの往復**と**解析対象の大きさに比例する処理**に何を足したかを見るエージェント。
性能には対応する分類の語彙が無いので、指摘の分類は `なし` にする。

共通の指示は `.claude/skills/implementation-flow/reviewer-instructions.md` に従う。

## 先に読むもの

`rules/` に性能だけを扱う節は無い。拠り所は次のとおりで、それ以外は**実害を数えて示せるもの**
だけを挙げる。

- `rules/architecture.md`「問い合わせの単位を答えの単位に揃える」
- `docs/tightrope-plan.md` — 対象にする規模（リポジトリの大きさ・言語）

---

## 指摘する範囲

**回数か規模のどちらかが伴う箇所だけを見る。** 1 回しか通らない処理の最適化は指摘しない。

| 経路 | 例 |
| --- | --- |
| LSP への問い合わせ | references・definition・hover。1 往復ごとにプロセス外の同期待ちが入る |
| git の起動 | `git log` の 1 回ごとにプロセスの起動と履歴の走査 |
| ファイル数に比例 | 構文解析・ファイルの読み込み |
| 依存の本数に比例 | 判定・`coupling.json` の組み立て・出力 |

## 問い合わせの観点

- **答えがファイル（またはプロジェクト）単位で決まる問い合わせを、参照・依存ごとに呼んでいないか。**
  同じキーで N 回尋ねていないか（`rules/architecture.md`「問い合わせの単位を答えの単位に揃える」）
- **git の履歴をファイルごとに `git log` で起動していないか。** 1 回の `git log` で全ファイルを読めないか
- **同じファイルを何度も読み直していないか**

## 計算量の観点

- **ループの中で `iter().find` / `contains` を呼び、依存の本数の 2 乗になっていないか。**
  `HashMap` / `HashSet` を 1 度作れば済まないか
- **不要な `clone()` / `to_string()` を、ファイル数・依存の本数に比例する経路で呼んでいないか**
- **安い除外より先に、重い判定（LSP への問い合わせ等）を候補ごとに呼んでいないか**

## 資源の観点

- **起動した子プロセス（LSP サーバ・git）を、失敗した経路でも終わらせているか（`wait` / `kill`）**
- **子プロセスの出力をすべてメモリに溜めてから読んでいないか**（巨大なリポジトリで膨らむ）

## 指摘の信頼度

**実測していない「遅い」は信頼度を「低」にする。** 信頼度を上げるには、その経路が何回
通るか、何件のファイル・依存で何回回るかを、コードから数えて示す。規模の想定を置いたら、
その値も書く。
