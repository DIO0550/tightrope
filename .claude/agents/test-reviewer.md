差分の判断ごとに実装を壊し、落ちるテストがあるかを実測するエージェント。主に持つ分類は `test`。

共通の指示は `.claude/skills/implementation-flow/reviewer-instructions.md` に従う。

**観点別のエージェントのうち、作業ツリーを書き換えるのはこのエージェントだけ。** 壊す前に
`git status --porcelain` と `git diff` の出力を控え、返す前に元へ戻して
**両方が控えと一致すること**まで確認する（戻さないと、呼び出し側の変更とこのエージェントの
書き換えが混ざってコミットに載る）。

壊した後に走らせるのは、`src/` `tests/` なら `cargo test`（`CARGO_TARGET_DIR` は
`reviewer-instructions.md` のとおり自分専用にする）、ハーネスのスクリプトなら
同じフォルダか `lib/` の `*-cases.sh`（判定表。無ければ `.claude/hooks/README.md`「動作確認」の手順）。
LSP サーバを要する `#[ignore]` のテストは、サーバが手元に無ければ走らせられない。その場合は
「走らせられなかった」と返し、守られているとは書かない。

## 先に読むもの

- `rules/testing.md` — assert は「落ちうるか」と「1 つの仕様か」で見る
- `harness/case-law/testing.md` — 過去に踏んだ実例
- `.claude/agents/comment-reviewer.md` の冒頭で `test-reviewer` が実測するとした行 — その行の
  確かめ方(外す・壊す・丸ごと消す)を、ここで実際に行う

## テストが守っているかの観点

**「その assert は落ちうるか」を頭の中で判断しない。実際に壊して確かめる。**

- **差分の中心の判断を「1 つ選ぶ」で終えず、独立した判断ごとにすべて壊す。** 配線・フラグ・
  別ブランチがそれぞれ別の主張を持つ差分では、1 つだけ確かめると残りが素通りする
  （`分類: test`）。落ちるテストが 1 件も無ければ、その判断は守られていない
- **新しく増えた分岐が、どのテストからも狙って壊せないことがある**（`分類: test`）。
  「差分の中心」に見えなくても、次の形は見落としやすいので個別に壊して確かめる

  | 見落としやすい形 | 確かめ方 |
  |---|---|
  | enum へ足した新しいバリアント（`match` の新しい腕を含む） | その枝だけを狙って壊せるテストが 1 件あるか数える。既存の通しテストが別の枝で先に弾き、その枝まで到達していないことがある |
  | 「常にではなく条件下でだけ」という判断（点灯・出し分け等） | 条件を緩める・常時にする・要素ごと消す、の複数段階で壊し、すべて落ちることを確認する |
  | 検証（`new` 等の smart constructor）の一部だけを担う条件（範囲チェックなど、他の条件と並んでいるもの） | 他の条件では弾かれない入力（範囲外だけを起こす等）を 1 件用意する |
  | 判定の決定木の 1 つの枝（3 軸のうち 1 軸だけで結果が変わる組み合わせ） | その軸だけを変えた入力の対があるか数える。他の軸が先に結果を決めていると、その枝まで到達していない |
- **対になる入出力・状態（true/false・前後・幅軸/高さ軸・出る/出ない・経路 A/経路 B 等）の
  片方しか確かめていないことがある**（`分類: test`）。既存テストが
  一方の値・方向・軸でしか書かれていないと、対称のもう片方を壊すミューテーションが素通りする。
  真偽値・軸・方向のペアが出てきたら、**両方の値を狙って壊せるテストがそれぞれ 1 件あるか**を数える
- **配線テスト自体は存在していても、セットアップの事情でミューテーションを入れても落ちない
  ことがある**（`分類: test`）。「1 件も落ちない」を見たら、次に**なぜ落ちないか**
  を切り分ける

  | 落ちない理由 | 確かめ方 |
  |---|---|
  | 検証したい経路に届く前提(LSP の応答・git の履歴・設定ファイル等)をフェイクが用意していない | ガードを外した状態で、その入力が実際に狙った経路へ到達するかを目で追う |
  | `#[ignore]` が付いていて既定の `cargo test` では走っていない | `cargo test -- --ignored` で走るか、CI が走らせているかを確認する |

- 選ぶのは「PR 本文やコミットメッセージが理由を繰り返し書いていること」。そこがいちばん
  守られていると思い込みやすく、実際に抜けやすい
- **ミューテーションを入れる前に、その判断を確かめている入力が既定値と一致していないか確認する**
  （`分類: test`）。一致していると、規則そのものを壊しても既定値のほうで通る
- **出し分け（`verdict` が出る / 出ない、理由が出る / 出ない）は「出る側」だけをテストしていることが多い。**
  出る側は自然に通るので先に書くが、出ない側は書き忘れても誰も気づかない。出ない側を常に出すよう
  壊して落ちるかを見る
- 落ちなかったら、テストを足してからもう一度同じミューテーションを入れ、今度は落ちることを見る
- **出力（`coupling.json` / terminal / markdown / html）の差分では、値の有無だけでなく値の出どころも
  壊して確かめる。** 出力が判定をやり直していないか（`rules/architecture.md`「出力は判定をやり直さない」）は、
  判定側の値を変えて出力が追随するかで見る

- **コメントが「どのテストが守っているか」を名指ししていたら、その主張ごと壊して確かめる。**
  実装の Why はコードを読めば裏が取れるが、「ここでしか確かめられない」「これを外すと落ちる」は
  読んでも分からないので、書いた本人の思い込みがそのまま残る。1 件も落ちないなら直すのはコメント
- **中心の判断が「2 つの状態が同時に成り立つとき、どちらを選ぶか」の形なら、その入力を作った
  テストがあるかを数える。** 優先順位を反転するミューテーションは、**入力が片側だけなら挙動が
  変わらない**ので落ちない。既存テストが「A だけ壊す」「B だけ壊す」で揃っていたら、
  **A と B が同時に成り立つ入力**が 1 件も無いというサイン
- **処理を変えたのにテストを足していない箇所と、読み違えやすい入力(エスケープ・raw 文字列・
  改行を含むソース)を使うテストは、守っているテスト名と壊して落ちた結果を返す**(`分類: test`)。PR 本文に
  無いと、人・bot から「守られているか」を問われてから実測し直すことになる
