# `flow:feature`: 落ちるテストを先にコミットしてから作る

`flow:feature` の Issue で、`SKILL.md` の各フェーズに**足す**手順。書いていないフェーズは
`SKILL.md` のまま。

**実装より先に、足す振る舞いを表すテストを書き、落ちるのを確かめてコミットする**(理由と、Red の
コミットの数は `rules/tdd.md`「Red はコミットに残し、落ちたのを確かめてから Green へ進む」)。

## フェーズ 3: テストごとに、Red に入れるかと落ち方

テストケースの一覧の各テストに、次を書く。

- **Red に入れるか、Green の後に足すか。** 足す振る舞いを表すテストは Red に入れる。境界値・網羅の
  テストは Green の後に足してよい(`rules/tdd.md`「前提として守るもの（プラグイン側の再掲はしない）」)
- Red に入れるテストは、**置くファイルと、第 1 工程での落ち方**。落ち方は `SKILL.md` フェーズ 5 の
  a / b / c のどれでもよく、その表の「計画に書くこと」を書く
- **足す・形を変える API を呼ぶ既存のテストの書き換えは、Red に入れる**(落ち方は b)。Green の側に
  既存のテストの書き換えを置かない。Green で書き換えると、書き換えた後のテストは落ちたのを確かめていない
- **同じテストターゲットに a と b を混ぜない。** コンパイルエラーがあると、`cargo test` は
  `--no-fail-fast` を付けてもテストを 1 つも走らせないので、a が計画どおりに落ちるかを見られない。
  ターゲット(`--lib` の単体テストと、`tests/` のファイルごと)を分ければ、`cargo test --locked --lib` /
  `cargo test --locked --test <名前>` で片方ずつ走らせられる

### 第 1 工程に許す配線

第 1 工程はテストだけを書く(`SKILL.md` フェーズ 5)。新しいテストを走らせるのに要る配線は、次の
3 つに限って第 1 工程に含める。型・関数の中身は 1 行も置かない。

- 親モジュール(`src/lib.rs` か `src/<親>.rs`)の `mod` 1 行。可視性は計画したとおりに書く(公開するなら
  `pub mod`)。Red の `mod foo;` を Green で `pub mod foo;` に変えると、`SKILL.md` フェーズ 5「第 2 工程以降で
  確かめること」の配線の検査が `-mod foo;` を配線の削除として拾う
- `#[cfg(test)] mod tests;` だけを置いた `src/<名前>.rs`
- 新しい判定表を走らせる `harness/githooks/pre-push` の `run_check` 1 行

### Red が無いとき

第 1 工程を省いて `Red: 無し` にしてよいのは、次の 2 つだけ。どちらに当たるかを計画に書く。

- **文書だけ。** 走らせる検査を持つファイル(コード・テスト・判定表・スクリプト)を変えない
- **今ある API だけを呼ぶ、LSP を要する `#[ignore]` のテストだけ。** `pre-push` で走らないので
  (`SKILL.md` フェーズ 7)、落ちるのを見られない。新しい API を呼ぶなら、コンパイルはされるので b の Red になる

## フェーズ 5: 工程ごとに書かせるものと確かめること

2 つの工程の仕組みと確かめ方は `SKILL.md` フェーズ 5。

1. **第 1 工程: 計画で Red に入れたテストと、上の配線だけを書かせる。** 実装はさせない
   - Red に a と b の両方があるときは、`implementer` が `pre-push` の出力に加えて、ターゲットごとに
     `cargo test --locked --lib` / `cargo test --locked --test <名前>` を走らせた出力も返す。`pre-push` の `cargo test` は
     b のコンパイルエラーで止まるので、親は a の落ち方をターゲットごとの出力で照らす
   - b は、エラーが計画に書いた API を指しているかを次の表で見る

     | コード | エラーの文が名前を出すもの |
     | --- | --- |
     | E0425 | 見つからない関数・定数 |
     | E0433 | 解決できないパスの先頭(モジュール・型) |
     | E0432 | 解決できない `use` のパス |
     | E0599 | 見つからないメソッド・関連関数と、その型 |
     | E0560 | 構造体を作るときの、無いフィールドと構造体 |
     | E0609 | 読み出した、無いフィールドと型 |
     | E0277 | 満たされないトレイトと型 |

     E0061(引数の数)と E0308(型の食い違い)は、文に API の名前が出ない。エラーが指す行を読み、
     呼んでいるのが計画で形を変える API かを確かめる。表に無いコードも同じく行を読む

2. **第 2 工程: 実装させる。** Red のテストは書き換えさせない
