# `flow:feature`: 落ちるテストを先にコミットしてから作る

`flow:feature` の Issue で、`SKILL.md` の各フェーズに**足す**手順。書いていないフェーズは
`SKILL.md` のまま。

**実装より先に、足す振る舞いを表すテストを書き、落ちるのを確かめてコミットする**(理由は
`rules/tdd.md`「Red はコミットに残し、落ちたのを確かめてから Green へ進む」)。計画で Red に入れた
テストをまとめて第 1 工程に書き、テストごとに Red と Green のコミットを繰り返さない(やり直したときの
Red のコミットの扱いは `SKILL.md` フェーズ 5)。

## フェーズ 3: テストごとに、Red に入れるかと落ち方

テストケースの一覧の各テストに、次を書く。

- **Red に入れるか、Green の後に足すか。** 足す振る舞いを表すテストは Red に入れる。境界値・網羅の
  テストは Green の後に足してよい
- Red に入れるテストは、**置くファイルと、第 1 工程での落ち方**。落ち方は次の 3 つのどれか

| 落ち方 | 何で落ちるか | 計画に書くこと |
| --- | --- | --- |
| a | assert の失敗 | どの assert がどの値で落ちるか(期待した値と、実際に出る値) |
| b | 足す・形を変える API を指すコンパイルエラー | どの API を指して、どのコードで落ちるか(フェーズ 5 の表) |
| c | 判定表・テストのスクリプト(`*-cases.sh` / `*-test.sh`)の食い違い | どのケースの期待と実際が食い違うか |

- **同じテストターゲットに a と b を混ぜない。** コンパイルエラーがあると、`cargo test` は
  `--no-fail-fast` を付けてもテストを 1 つも走らせないので、a が計画どおりに落ちるかを見られない。
  ターゲット(`--lib` の単体テストと、`tests/` のファイルごと)を分ければ、`cargo test --lib` /
  `cargo test --test <名前>` で片方ずつ走らせられる

### 第 1 工程に許す配線

第 1 工程はテストだけを書く(`SKILL.md` フェーズ 5)。新しいテストを走らせるのに要る配線は、次の
3 つに限って第 1 工程に含める。型・関数の中身は 1 行も置かない。

- `src/lib.rs` の `mod` 1 行
- `#[cfg(test)] mod tests;` だけを置いた `src/<名前>.rs`
- 新しい判定表を走らせる `harness/githooks/pre-push` の `run_check` 1 行

### Red が無いとき

第 1 工程を省いて `Red: 無し` にしてよいのは、次の 2 つだけ。どちらに当たるかを計画に書く。

- **文書だけ。** 走らせる検査を持つファイル(コード・テスト・判定表・スクリプト)を変えない
- **今ある API だけを呼ぶ、LSP を要する `#[ignore]` のテストだけ。** `pre-push` の `cargo test` は
  `#[ignore]` を走らせないので、落ちるのを見られない。`#[ignore]` でもコンパイルはされるので、
  新しい API を呼ぶなら b の Red になる

## フェーズ 5: 工程ごとに書かせるものと確かめること

2 つの工程に分ける仕組み(工程の渡し方・第 1 工程のコミットと `TDD: red`・第 2 工程以降で確かめること)は
`SKILL.md` フェーズ 5。

1. **第 1 工程(`工程: Red`): 計画で Red に入れたテストと、上の配線だけを書かせる。** 実装はさせない
   - 返ってきた検査の出力で、**Red のテストが計画に書いた落ち方で落ち、それ以外の検査(`pre-push` の残り)が
     通っている**ことを親が確かめる。b のときは `clippy` も同じコンパイルエラーで落ちるので、それは
     Red の落ち方に数える。通った・計画と違う落ち方をした・他のテストも落ちた、のどれかなら Red に
     なっていないので、計画へ戻す
   - a は落ちた assert と値を、c は食い違ったケースを、計画と照らす。b は、エラーが計画に書いた API を
     指しているかを次の表で見る

     | コード | エラーの文が名前を出すもの |
     | --- | --- |
     | E0425 | 見つからない関数・定数 |
     | E0433 | 解決できないパスの先頭(モジュール・型) |
     | E0432 | 解決できない `use` のパス |
     | E0599 | 見つからないメソッド・関連関数と、その型 |
     | E0560 | 構造体を作るときの、無いフィールドと構造体 |
     | E0609 | 読み出した、無いフィールドと型 |
     | E0277 | 満たされないトレイトと型 |

     E0061(引数の数)と E0308(型の食い違い)は、文に API の名前が出ない。エラーが指す行を読み、
     呼んでいるのが計画で形を変える API かを確かめる。表に無いコードも同じく行を読む

2. **第 2 工程(`工程: Green`): 実装させる。** Red のテストは書き換えさせない
   - 返ってきたら `SKILL.md` フェーズ 5「第 2 工程以降で確かめること」を走らせ、Red のテストが通って
     いることを返ってきた検査の結果で確かめる
