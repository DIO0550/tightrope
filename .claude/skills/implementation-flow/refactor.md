# `flow:refactor`: 振る舞いを変えず、既存のテストで確かめる

`flow:refactor` の Issue で、`SKILL.md` の各フェーズに**足す**手順。書いていないフェーズは
`SKILL.md` のまま。

**振る舞いが変わっていない根拠は、書き換えていない既存のテストだけ。** テストを実装と一緒に
書き換えると、緑のままでも振る舞いが変わっていないとは言えなくなる。

## 書き換えない範囲

**書き換えない範囲**はテストとその共有物・判定表・テストの配線。下のコマンドの pathspec
(単体テスト・統合テスト・判定表とその共有物)は、ファイルごと書き換えない範囲。Rust の単体テストは
`mod tests;` が指す `tests.rs` とその下の `tests/` に置く(`rules/testing.md`。`test-placement.sh` が
それ以外を落とす)ので、パスで切り出せる。複数の `tests.rs` が共有するテスト専用モジュールを
その外に置いたなら、そのパスを計画に書いて下のコマンドに足す。

**テストを走らせる配線**は、`SKILL.md` フェーズ 5「第 2 工程以降で確かめること」の 2 つ目のコマンドが
拾う行。下のコマンドとその 2 つ目を、フェーズ 5 で親が走らせる。

```bash
git diff <第 1 工程のコミット> HEAD -- tests ':(glob)src/**/tests.rs' ':(glob)src/**/tests/**' \
  ':(glob)**/*-cases.sh' ':(glob)**/cases-fixtures.sh' ':(glob)**/cases-report.sh'
```

書き換えない範囲で**しないこと**:

- assert を含むテストの本文(期待値・入力・テストの名前)を変えない。下の「してよいこと」に
  当たる書き換えだけが例外
- テストを消さない(skip を含む)。配線も消さない(移動表にある移動の片割れを除く)
- 参照先を別の実装・スタブへ向け替えない

書き換えない範囲で**してよいこと**(これ以外はしない):

- テストを足す
- 計画の移動表にあるファイルを移動する。移動に伴う中身の変更は、下の 2 つに当たるものに限る
- 参照先(`use` のパス・`mod` の位置)を、計画の移動表にある移動先へ書き換える。同じものを
  指したまま場所が変わる書き換えに限る
- 計画の改名表(旧名 → 新名)にある名前を、本文の中でも書き換える。表に無い名前を変えると、
  `parse` → `parseLoose` のような向け替えが改名に紛れて読めなくなる

## フェーズ 3: 計画に足すもの

- **守っている既存テスト。** 触るコードを守っているテストのファイルと、走らせるコマンドと件数
- **現状を固定するテスト。** 守っている既存テストが無い範囲には、今のコードで通るテストを
  先に足す計画にする。足すものが無いなら「無し」と書く(フェーズ 5 の第 1 工程を省く)
- **移動表**(ファイル・モジュールの移動元 → 移動先)と**改名表**(旧名 → 新名)。
  無いなら「無し」と書く
- 仕様の変更や既存テストの書き換えが要ると分かったら、`flow:refactor` に合わない作業なので
  計画せずに止め、`SKILL.md` フェーズ 1「種類の確定」の 6 に従う

## フェーズ 5: 工程ごとに書かせるものと確かめること

2 つの工程に分ける仕組み(工程の渡し方・第 1 工程のコミット・第 1 工程を省くとき・第 2 工程以降で
確かめること)は `SKILL.md` フェーズ 5。第 1 工程は通るのが正しいので、`TDD: red` は付けない。

1. **第 1 工程(`工程: 現状の固定`): 現状を固定するテストだけを足させる。** 今のコードのまま、
   足したテストを走らせる検査が通ることを返させる。計画の現状を固定するテストが「無し」なら省く
2. **第 2 工程(`工程: リファクタ`): リファクタさせる。** commit したら、親が「書き換えない範囲」の
   コマンドと、`SKILL.md` フェーズ 5「第 2 工程以降で確かめること」の 2 つ目の出力を読む
   - 「書き換えない範囲」のコマンドに出てよいのは、足したテストと、「してよいこと」に当たる書き換えだけ
   - 配線のコマンドに出た行は、移動表にある移動の片割れかを確かめる
   - 外れていたら、外れた行を指摘として `implementer` に戻す

このコマンドは読む作業を減らさない。`use` の書き換えを取り除いてから比べる検査が欲しくなったら、
判定表つきのスクリプトにする(判定表を持たないコードをこの文書に埋めない)。

## フェーズ 6: 直しでも既存テストを変えない

- 採用した指摘を直すときも、「書き換えない範囲」の決まりは同じ。テストが足りないという指摘には、
  既存テストを書き換えず新しいテストを足して応える
- 直しのたびに、フェーズ 5 の 2 つのコマンドの出力を読み直す
- **`test-reviewer` はそのまま呼ぶ。** 振る舞いが変わっていない根拠は既存テストだけなので、
  それが実装を守っているかを実測する役が要る

## フェーズ 7: 出力の形を変えない

- **CLI の出力(text / JSON)を固定しているテストの期待値を変えない。** 出力が変わったなら、それは
  振る舞いの変更なので直す対象。出力の形を変えたいなら `flow:refactor` ではなく別の Issue にする
