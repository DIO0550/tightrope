# コーディング規約

**前提**: 所有権・借用・`Result` / `?`・命名など**言語共通の Rust 規約は d-market-rust の
`coding-standards` スキルが持つ**。ここに書くのは、それに足す・逸脱する分だけ
（`AGENTS.md`「規約の持ち場」）。
実例（過去に踏んだ形）は [`harness/case-law/coding.md`](../harness/case-law/coding.md)。

## 前提として守るもの（プラグイン側の再掲はしない）

- 早期 return でネストを浅くする
- `cargo clippy --all-targets -- -D warnings` の警告をすべて解消する
- マジックナンバーは定数化する
- 参照を優先し、変更が要るときだけ `&mut`
- `let` を基本にし、`mut` は必要な場合のみ
- 失敗は `Result`、伝播は `?`

## エラーと不在の表現

### `unwrap()` / `expect()` は本番コードで使わない

**この禁止はツールが落とす。** 根の `Cargo.toml` の `[workspace.lints.clippy]` が `unwrap_used` /
`expect_used` を `deny` にし、`clippy.toml` の `allow-unwrap-in-tests` /
`allow-expect-in-tests` がテスト内だけ許可する。

**Why**: 「規約に書いてある」だけでは、読まれなかった回に通ってしまう。
ツールで落とせるものは規約の文に留めない（`AGENTS.md`「強制力の序列」）。

### 不在は `Option`、失敗は `Result`

- 「見つからない」「まだ取れていない」は `Option`
- 「やってみたが駄目だった」で、**呼び出し側が理由で分岐しうる**なら `Result`
- **失敗を握りつぶして既定値へフォールバックしない。** 呼び出し側が分岐できるよう、そのまま伝播させる

たとえば「行番号が数字でない」と「行番号が 0」は、どちらも「行番号が駄目」だが、
**利用者が直す先が違う**ので 1 つのバリアントにまとめない。

### エラー型は原因ごとにバリアントを分ける

`String` 1 本のエラーにしない。**呼び出し側が分岐できる粒度**でバリアントを切り、
`Display` で人が読む文にする。バリアントが持つ値は「読めなかった文字列」など
**直すために要る情報**に限る。

## 生成時に検証し、不正な値を存在させない

制約を持つ値は、**生成する関数が検証込みで作る**（Smart Constructor）。
検証に失敗しうるなら `Option` / `Result` を返し、「生成された = 制約を満たしている」を成立させる。
生成後に呼び出し側が検証する設計にしない（検証を通っていない値が型上は同じ顔で流通する）。

```rust
// OK: 範囲外・NaN では作れない。作れた時点で 0.0-1.0 が保証される
impl Threshold {
    pub fn new(value: f64) -> Option<Self> {
        if value.is_nan() || !(0.0..=1.0).contains(&value) {
            return None;
        }
        Some(Self(value))
    }
}
```

- **自前のラッパを作る前に標準を探す。** 「0 が存在しない」だけなら `NonZeroUsize`、
  「範囲が決まっている」だけなら既存の型で足りることが多い
- **標準の型が「その値の意味」まで言えないなら newtype にする。** 判断軸は
  **その型に置き場所が要る操作があるか**
- **型が構造で狭まっているかを確かめる。** `type Score = f64;` のような別名は
  素の `f64` がそのまま代入できるので、**何も防いでいない**

**Why not（標準の型のまま通す）**: 変換や判定が要る場所ごとに同じ private ヘルパーが生え、
0 始まりと 1 始まりの取り違えのような誤りが、**どちらも `usize` なので型では止まらない。**

## 値の語彙を型で閉じる

取りうる値が仕様上決まっているものを `String` / `f64` のままにしない。

このツールが扱う語彙はほぼ決まっている。**enum にする。**

| 語彙 | 型 |
|---|---|
| 判定 | `enum Verdict { Risk, Warn, Tolerated, Ok }` |
| 統合強度 | `enum Strength { Intrusive, Functional, Model, Contract }` |
| 対象言語 | `enum Language { .. }` |
| 出力形式 | `enum OutputFormat { .. }` |

- **スコアと閾値を素の `f64` で混ぜない。** 取り違えても型エラーにならない
- **まだ動かない選択肢を enum に並べない。** 選べるのに何も変わらない値がヘルプに出ると、
  使う側は「指定が効いていない」と「未対応」を区別できない。
  **選択肢と、それが変える振る舞いは同じ差分に入れる**

## 不正な状態を型で表現できなくする

矛盾した状態が作れてしまうなら、取りうる状態を**判別可能な enum で列挙**する。

```rust
// NG: 「取れていないのにスコアがある」「取れたのにスコアが無い」が表現できる
struct Signal { available: bool, score: f64 }

// OK: スコアを持つのは取れたときだけ、が構造に出る
enum Signal {
    Unavailable { reason: UnavailableReason },
    Measured { score: Similarity },
}
```

`match` は `_` の受け皿を置かずに書く。バリアントを足したときに**黙って既存の枝へ落ちない**
（コンパイルエラーになる）。網羅のためだけの `_ => unreachable!()` は書かない。

## 列挙で判定を組むときは、漏れの倒れる向きを選ぶ

**許可リスト・拒否リストで判定を書くとき、一覧に無い形がどちらへ倒れるかを先に決める。**
一覧は対象の文法が持つ形の数だけ増え続けるので、**漏れは前提として設計する。**
漏れが安全側に倒れる向きを選ばないと、文法の形を 1 つ見つけるたびに指摘が続く。
「安全側」はその判定が何を出すかで決まる（強い結合を見落とすのか、弱い結合を強いと言うのか）ので、
判定ごとに書く。

- **同じ一覧を、安全な倒れ方が違う 2 箇所で使い回さない。** 漏れたときに「何もしない」側と
  「数えに入れる」側では、安全な向きが逆になる
- 判断軸: **一覧を空にしたとき、判定は安全側に倒れるか。** 倒れないなら、許可リストと
  拒否リストのどちらで書くかを反転する

## コメントは doc だけにする

Rust のコードに書くコメントは **doc（`///` / `//!`）だけ**。通常のコメント（`//`）と、doc の中の
Why / Why not は書かない（`harness/githooks/lib/comment-style.sh` が落とす）。ハーネスのスクリプトは対象外。

### doc に書く項目

Rust の慣習に従い、rustdoc の書式で書く（JSDoc の `@param` は使わない）。

| 持っているもの | 書くこと |
|---|---|
| 引数 | その引数が何を表すか。**型の再掲は書かない** |
| 戻り値 | 何を返すか。`Option` / `Result` なら**どんなときに `None` / `Err` になるか** |
| `Result` を返す | `# Errors` セクション |
| パニックしうる | `# Panics` セクション |

### doc に書かないもの

| 書かないもの | 置く先 |
|---|---|
| なぜその形にしたか（Why）・捨てた案（Why not） | Issue（計画と却下案）・コミットメッセージ |
| 経緯・実行履歴・Issue の番号 | Issue / PR |
| What の言い換え・コード内の値の再掲・一般論 | どこにも書かない |

**判断軸は「呼ぶ側が使い方を知るのに要るか」**（何であるか・何を受け取り何を返すか・いつ失敗するか）。

## 禁止事項

- **lint 抑制を足さない**（`#[allow(..)]` / `#[expect(..)]`）。
  抑制したくなったら**設計のほうを変える**（`dead_code` が出たら lib + bin に分ける、が典型）
- `unsafe`

## I/O を持ってよい場所

ファイルの読み書き・子プロセス（LSP サーバ・git）の起動は**I/O の境界だけ**が持ち、受け取ってから先は純粋な関数に切る。
I/O の境界の一覧は文で持たず、`rules/architecture.md`「依存方向のルール（必須要件）」の表の検査が持つ。

**Why**: 渡す先が純粋なら、テストが実ファイルや実サーバを要求しない（`rules/testing.md`
「モックは使わない」と `rules/tdd.md`「LSP は『応答を受け取ってから先』を切り出す」）。
`fs::` / `Command::new` を grep するだけで I/O の入口を数え切れる形を保つ。

## 外部の挙動は動かして確かめる

シェル・CLI・LSP サーバ・git・外部フォーマット（JSON 等）の挙動を前提にしたコード（CI・フック・
lint 設定を含む）は、**正しく動くはずという想定だけで書かない。** 依存する挙動を小さく再現して
確かめてから使う。

## 規約の適用範囲

**この規約は `crates/` の Rust だけでなく、`.claude/hooks/` `.github/scripts/` `harness/` など
ハーネス自身を実装しているコード・doc にも及ぶ。**

- ブロックのネストを浅く保つ・条件式に名前を付ける、は対象言語（bash 等）を問わず適用する
- 「同じ処理が 2 箇所に現れたら共通化する」は、**同じ判断根拠を説明する doc・README の重複**
  にも適用する。片方だけを直せる状態を作らない
